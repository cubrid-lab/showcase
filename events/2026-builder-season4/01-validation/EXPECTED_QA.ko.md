# 1차 검증 질의응답 준비

기준: 2026-10-20 · 발표 10분 이후 Q&A 10분. 모든 답변을 순서대로 읽는
대본이 아니라, 질문에 맞춰 30–60초씩 답하는 참고 자료입니다.
근거와 실행 환경은 [SOURCES.md](SOURCES.md)에 고정했습니다.

## 1. 누구의 문제인가요? 실제 수요를 확인했나요?

초기 대상은 CUBRID DB 운영자와 Kubernetes 플랫폼 팀입니다. 장애 뒤 역할·복제·
데이터와 접속 경로를 함께 확인하는 반복 작업을 줄이려 합니다. 아직 고객 인터뷰나
도입 사례로 수요를 검증했다고 주장하지 않습니다. 이번 검증에서는 실제로 가장
비용이 큰 장애 대응 절차와, 다음 검증에 참여할 운영 환경을 확인하고 싶습니다.

## 2. 공식 CUBRID Operator가 있는데 왜 별도로 만드나요?

공식 Operator도 HA 역할 관찰, 스토리지, 예약 백업을 제공합니다. 이 프로젝트는
관찰 누락·불일치와 복구 중단 상황에서 판단과 결과를 재현 가능한 증거로 확인하는
실험입니다. 공식 프로젝트보다 안정적이라고 입증하거나 대체를 선언한 것은 아닙니다.
구현과 실험 결과를 공개해 기존 생태계에도 참고할 수 있게 하려 합니다.

근거: [공식 구현](https://github.com/CUBRID/cubrid-operator/tree/fa7b6c2cf26096769c4404a2e2bb683f3872aa1e).

## 3. 지금 실제로 실행되는 것은 무엇인가요?

검토된 PR head에서 Kind E2E 27개가 통과했습니다. 별도로 실제 VM Kubernetes에서
선택한 이미지로 LAB00 SQL 연결 검사와 HTTP 연결 제한 검사를 실행했습니다.
기존 demo·HA를 순차 교체한 뒤 알려진 행과 타임스탬프 유지, 새 RW 커밋의 RO 반영,
RO 쓰기 거부도 확인했습니다. 각 환경과 검증 범위를 따로 기록했습니다.

27개는 테스트 spec 수이며 필수 시나리오 S00–S15 전체 통과라는 뜻이 아닙니다.

근거: [Kind 실행](https://github.com/cubrid-lab/cubrid-kubernetes-operator/actions/runs/39348551910),
[VM 결과](https://github.com/cubrid-lab/cubrid-kubernetes-operator/issues/301#issuecomment-6281421472).

## 4. 그러면 VM 장애에도 안전하고 운영에 쓸 수 있나요?

아직 그 결론을 내릴 수 없습니다. 이번 VM 환경은 local-path 스토리지이고 LAB00은
설치된 Operator의 연결 검사입니다. VM 전원 차단·네트워크 분할·선정 CSI·전체
필수 시나리오와 장시간 운전 검증은 별도입니다. 현재 프로젝트는 experimental입니다.
기존 랩의 pycubrid 클러스터도 데이터 가시성 문제 때문에 이미지 갱신을 보류했습니다.

## 5. Operator가 master를 승격하나요? split-brain은 어떻게 다루나요?

역할 전환은 CUBRID native HA가 수행합니다. Operator는 그 결과를 관찰하고 자원과
작업을 조정합니다. 멤버 0을 영구 master로 취급하거나, 불완전한 관찰만으로 승격하거나,
갈라진 데이터 중 하나를 선택하지 않습니다. 관찰 상태 보고와 실제 쓰기 격리는 다르며,
분할 상황에서 RW 쓰기를 실제로 차단·해제하는 정책과 검증은 남은 필수 작업입니다.
정상 RO 접속에서 INSERT가 거부된 결과로 이 공백이 해결됐다고 말하지 않습니다.

근거: [ADR-0005](https://github.com/cubrid-lab/cubrid-kubernetes-operator/blob/39b1cb6ca7b6a52cf933b778c546cd9d6c6979bb/docs/adr/0005-failover-split-brain.md),
[쓰기 격리 #113](https://github.com/cubrid-lab/cubrid-kubernetes-operator/issues/113).

## 6. 무손실이나 복구 시간, 백업 복원을 보장하나요?

현재 일반적인 무손실·RPO·RTO를 보장하지 않습니다. 알려진 데이터 보존 관찰은
해당 실험의 결과입니다. HA 초기 seeding, 백업 업로드 단위·스토리지 테스트와
실제 CubridBackup에서 새 클러스터로 복원하는 전체 시나리오도 구분합니다.
성공·실패·결과 불명 요청을 구분한 트랜잭션 이력과 실제 장애·복원 증거가 필요합니다.

## 7. 보안은 어디까지 구현됐나요?

IM API bearer 인증과 비루트 실행은 DB 접속 인증이나 TLS와 별개입니다. 기준 코드의
README는 암호화되지 않은 통신과 빈 DBA 비밀번호를 명시하고 있습니다.
NetworkPolicy도 네트워크 플러그인이 강제해야 효력이 있습니다. 운영 보안이
완성됐다고 말하지 않으며, 첫 버전의 지원 환경과 보안 한계를 문서에 명시해야 합니다.

근거: [현재 네트워크 경계](https://github.com/cubrid-lab/cubrid-kubernetes-operator/blob/39b1cb6ca7b6a52cf933b778c546cd9d6c6979bb/README.md#network-access).

## 8. 12월 27일에 어디까지 공개하나요? 일정이 밀리면요?

목표는 CUBRID 11.4.x/amd64, Kubernetes 한 구성과 CSI 한 구성에서 HA·접속·장애
복구·쓰기 격리·재합류·재구축·백업과 새 클러스터 복원을 재현하는 v0.1입니다.
11월 29일에 필수 시나리오의 첫 전체 통과를 만들고, 12월에는 동일 후보의 반복 장애,
초기 목표 24시간 부하, 다른 메인테이너의 문서 재현과 회귀 수정을 진행할 계획입니다.
이 날짜들은 목표입니다. 핵심 안전 조건을 달력 때문에 빼거나, 검사하지 않은 것을
통과로 바꾸지 않습니다. 충족 여부로 공개 시점과 지원 범위를 판단합니다.

근거: [고정 ROADMAP](https://github.com/cubrid-lab/cubrid-kubernetes-operator/blob/39b1cb6ca7b6a52cf933b778c546cd9d6c6979bb/ROADMAP.md).

## 9. 두 사람은 어떻게 역할을 나누나요?

최영선과 백경준이 공동 메인테이너로 설계·개발·검증을 함께 맡습니다. 작업 단위로
담당자가 구현·테스트·관련 문서를 준비하고, 다른 메인테이너가 리뷰합니다.
특정 개인의 전문 영역이나 확정되지 않은 기능 배정을 임의로 발표하지 않습니다.

## 10. 이번 자리에서 어떤 도움을 원하나요?

실제 운영자가 가장 먼저 줄이고 싶은 장애 대응 절차, 기준 환경으로 검증할 CSI와
설정, 반복 실험과 문서 재현에 참여할 환경·동료에 대한 의견을 구합니다.
아직 고객 사례나 채택 실적이 있는 것으로 표현하지 않습니다.
