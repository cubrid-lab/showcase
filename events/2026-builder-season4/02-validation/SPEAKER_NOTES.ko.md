본편 20장, 설명 배정 9분 30초입니다. 전환·호흡에 30초를 남겨 전체 10분 안에 마칩니다. 시간은 배정값이며 실제 낭독으로 확인해야 합니다. 장마다 **요지**(이 장에서 남길 한 가지), **말할 것**(발표 노트 그대로), **넘어가기**, **질문 나오면**(예상 질문 번호)을 적었습니다.

## 한 문장으로 정리한 발표

서버 상태가 불확실하면 쓰기 연결을 닫고, 복구 뒤에는 성공 응답을 받은 데이터가 남았는지 확인합니다. 차단 전 손실과 중단 시간은 시험 조건과 함께 공개합니다.

## 장별 스크립트

### 1. CUBRID K8s Operator  (25초)

- **요지.** 오늘 할 말 한 줄: 불확실하면 쓰기를 멈추고, 장애 뒤 복구를 데이터로 확인한다.
- **말할 것.**

  > 안녕하세요. CUBRID Lab의 최영선, 백경준입니다. 저장 성공 응답을 받았는데, 장애 뒤 그 데이터가 없다면 어떨까요? 저희는 Kubernetes에서 CUBRID 운영과 복구를 관리하는 Operator를 만들고 있습니다. 오늘은 쓰기 연결을 막고 복구를 확인한 결과, 그리고 아직 막지 못한 손실을 말씀드리겠습니다.

- **넘어가기.** 인사 후 바로 2장으로.

### 2. 상태 표시에서 실제 차단과 복구로 나아갔습니다  (25초)

- **요지.** 상태 표시에서 실제 쓰기 차단과 요청에 따른 데이터 복구로 나아갔다.
- **말할 것.**

  > 1차에서는 서버 상태가 불확실하다는 표시까지만 했습니다. 이번에는 쓰기 연결을 실제로 차단하고, 데이터를 잃은 서버를 요청에 따라 복구하도록 구현했습니다. 구현한 기능은 자동 시험과 실제 장애 시험으로 확인했습니다. 먼저 왜 쓰기를 막아야 하는지부터 설명하겠습니다.

- **넘어가기.** "그중 가장 큰 변화가 쓰기 격리입니다" → 3장.

### 3. 불확실하면, 확인될 때까지 쓰기를 막습니다  (45초)

- **요지.** 복제 전에 장애가 나면 성공한 쓰기도 새 master에 없을 수 있다. 불확실할 때 연결을 끊되, 차단 전 쓰기까지 보호하지는 못한다.
- **말할 것.**

  > 현재 쓰기를 받는 DB 서버를 master라고 부릅니다. 나머지 서버는 그 데이터를 복제합니다. 저장 성공 응답을 받았더라도 복제가 끝나기 전에 장애가 나면, 새 master에는 그 데이터가 없을 수 있습니다.
  > 그래서 누가 쓰기를 받아도 되는지 불확실하면 쓰기 연결을 끊습니다. 이것이 쓰기 격리입니다. 애플리케이션은 성공 대신 연결 실패를 받고, 안전을 확인한 뒤 다시 쓸 수 있습니다. 읽기 전용 Broker와 -ro Service는 쓰기 격리의 영향을 받지 않습니다. 다만 차단 전에 이미 성공한 쓰기까지 보호하는 것은 아닙니다.

- **넘어가기.** "그럼 어떻게 닫는지 구조로 보겠습니다" → 설계.
- **질문 나오면.** 예상 질문 2, 6번.

### 5. Operator가 상태를 확인하고 연결을 관리합니다  (40초)

- **요지.** Operator는 SQL을 중계하지 않는다(위: 제어, 아래: 데이터). 바꾼 건 두 곳: Broker를 0개로 줄이는 쓰기 격리, 빈 멤버를 master 백업으로 채우는 재구축. master는 CUBRID가 뽑는다.
- **말할 것.**

  > 그림 아래가 데이터가 오가는 경로입니다. 애플리케이션은 DB 연결 창구인 Broker를 거쳐 CUBRID에 데이터를 저장합니다. 위쪽의 Operator는 운영을 관리하는 프로그램입니다. 각 DB 서버에 붙어 있는 Instance Manager에 상태를 묻고, 불확실하면 쓰기용 Broker를 중지합니다.
  > master를 고르고 데이터를 복제하는 일은 CUBRID가 맡습니다. Operator는 그 상태를 확인해 연결을 관리하고, 데이터를 잃은 서버의 복구를 조정합니다.

- **넘어가기.** "격리가 어떻게 시작되고 풀리는지" → 6장.
- **질문 나오면.** 예상 질문 7번.

### 6. 연결을 끊고, 확인한 뒤 다시 엽니다  (45초)

- **요지.** 관찰 → 차단(Broker 0) → 검증(쓰기 승인 0건) → 해제(자동 두 번 확인 또는 이번 격리 전용 토큰). '닫힌 뒤 승인 0건'이 안전 규칙.
- **말할 것.**

  > 쓰기 격리는 닫는 것만으로 끝나지 않습니다. master가 불확실하거나 삭제된 멤버를 아직 확인하지 못하면, 쓰기용 Broker를 0개로 줄입니다. 그리고 기존 연결과 새 연결 모두에서 저장 성공 응답이 없는지 확인합니다.
  > 다시 여는 조건도 정했습니다. 멤버 미확인으로 닫은 경우에는 같은 단일 master와 다른 멤버의 안전 근거를 10초 이상 간격으로 두 번 확인해야 자동으로 엽니다. master가 여러 개인 경우 등은 사람이 판단하고, 이번 격리에만 쓸 수 있는 일회용 토큰으로 해제합니다.

- **넘어가기.** "볼륨을 잃은 멤버는" → 7장.

### 7. 데이터를 잃은 서버는 요청에 따라 복구합니다  (40초)

- **요지.** 데이터 없는 멤버를 자동으로 덮어쓰지 않는다. 사람이 요청하면 master 백업으로 채우고 행을 대조한다. Kind에서 40.2초/48.9초, 기준 5분.
- **말할 것.**

  > 프로그램이 다시 뜨는 것과 데이터를 되살리는 것은 다릅니다. 이번 시험에서는 Pod가 삭제된 멤버가 자동으로 돌아왔습니다. 반면 데이터 볼륨까지 잃은 경우에는 사람이 대상을 확인하고 복구를 요청해야 합니다.
  > 요청하면 현재 master의 백업으로 데이터를 채우고, 복제하는 서버로 합류시킵니다. 시험에서는 복구 뒤 실제 데이터도 대조했습니다. 컨테이너로 구성한 Kubernetes 시험 환경인 Kind에서 복구는 40.2초, 데이터 확인까지는 48.9초였습니다. v0.1 기준은 5분입니다.

- **넘어가기.** "이제 어떻게 시험했는지" → 8장.

### 8. 성공 응답을 받은 데이터가 남았는지 확인합니다  (30초)

- **요지.** 왜: 앱이 받은 성공이 장애 뒤에도 남는지가 기준. 어떻게: Kind(main마다) + VM 랩(전원·분할·Pod 삭제·Operator 재시작). 무엇을: 승인된 쓰기를 멤버마다 행 단위 대조.
- **말할 것.**

  > 시험에서는 성공 응답을 받은 쓰기를 기록하고, 장애 뒤 각 서버에 그 데이터가 남아 있는지 대조합니다. 연결을 닫은 뒤에는 성공 응답이 없어야 합니다.
  > Kind에서는 코드 변경마다 자동 시험을 돌립니다. 실제 전원 차단과 네트워크 정책은 VM 세 대의 랩에서 따로 확인합니다. 랩은 공유 자원이라 사용 권한인 Lease를 확보하고 한 번에 하나씩 시험합니다.

- **넘어가기.** "먼저 공식 operator와 같은 장애를 낸 결과" → 9장.

### 9. 두 번째 장애에서 결과가 달라졌습니다  (40초)

- **요지.** 그래프 하나만 기억: 두 번째 삭제 뒤 공식(파랑)은 0에서 안 올라왔고(31분 master 없음), 우리(주황)는 승인 사이의 최장 공백이 32.8초였고, 격리 이후 첫 승인은 삭제 후 42.5초에 기록됐다. 대신 첫 삭제 중단은 우리가 더 길다(22초 vs 12초) — 확인 전까지 닫기 때문.
- **말할 것.**

  > 같은 VM 랩에서 쓰기 중 master Pod를 두 번씩 삭제했습니다. 그래프는 두 번째 시험입니다. 공식 Operator는 새 master를 선출하지 못해 31분간 쓰지 못했습니다. 저희는 세 멤버가 자동 복귀했고 쓰기도 재개됐습니다.
  > 주황 선은 삭제 직후 잠시 쓰기를 받다가 확인을 위해 닫힌 모습입니다. 쓰기 승인 사이의 최장 공백은 32.8초였고, 격리 뒤 첫 쓰기 승인은 삭제 후 42.5초에 기록됐습니다. 첫 시험의 중단은 저희가 22초로 공식의 12.4초보다 길었습니다. 두 시험 모두 쓰기 손실은 없었지만, 모든 장애에서 복구된다는 뜻은 아닙니다.

- **넘어가기.** "나머지 VM 시험 결과" → 10장.
- **질문 나오면.** 예상 질문 3, 4, 14번. 초기 구성은 공식 Operator에서 DB 생성·HA 시작·Broker 시작을 멤버마다 수동 실행했고, Lab Operator는 수동 단계 없이 약 2분이었습니다. 원 기록에서는 두 번째 장애의 원인을 멤버별 노드 목록 순서 차이로 설명합니다. 네트워크 분할은 이 비교에 포함하지 않았습니다.

### 10. VM 랩에서 확인한 동작과 측정값입니다  (30초)

- **요지.** VM 랩 실제 장애 다섯 가지. 안전 규칙은 통과, 시간은 측정값으로 공개. 사라진 쓰기는 13장에 모아 둠.
- **말할 것.**

  > VM 랩에서는 네트워크가 끊긴 동안 Operator를 재시작해도 쓰기 차단이 유지되는지 확인했습니다. 볼륨을 교체한 뒤의 복구와 새 클러스터로의 복원도 통과했습니다.
  > 전원 차단은 세 번 측정했고, 차단 표시부터 첫 쓰기까지 26초에서 38초였습니다. 다시 장애를 냈을 때는 이전 격리의 해제 토큰 두 개가 모두 거부됐습니다. 시간은 측정값으로 공개하고, 닫힌 뒤 저장 성공 응답이 없는지는 통과와 실패로 판정합니다.

- **넘어가기.** "이걸 매번 회귀로 지키는 게 Kind" → 11장.
- **질문 나오면.** 예상 질문 11번.

### 11. 자동 시험 61개로 같은 위험을 반복 확인합니다  (20초)

- **요지.** Kind E2E 61/61 (1차 27개). 1차에서 본 위험(master 삭제 중 쓰기)을 매번 다시 시험.
- **말할 것.**

  > 자동 시험은 1차의 27개에서 61개로 늘었고, 확인한 빌드에서는 모두 통과했습니다. 하지만 시험 통과가 모든 장애에서 데이터 손실이 없다는 뜻은 아닙니다. 실제 환경에서 찾은 결함과 남은 한계를 이어서 보여 드리겠습니다.

- **넘어가기.** "Kind로는 못 잡는 결함을 VM 랩이 잡은 사례" → 12장.
- **질문 나오면.** 전체 실행 약 63분 (main 3806d1db, 11월 25일). 11월 10–20일 실패 실행 58건 중 9건이 로컬 소켓 세션 끊김이었으며, 11월 22일 TCP 전환 후 기존 기록상 같은 원인 재발은 없었습니다. 짧은 관찰 기간의 결과입니다. 재구축 중 역할 확인 지연은 원인을 드러내도록 테스트를 개선했습니다.

### 12. VM 랩이 찾아낸 결함: 생존 확인 패킷 차단  (40초)

- **요지.** Broker 용량을 재다가 연결이 끊기는 걸 발견 → 층별로 나눠 원인(TCP 7 생존 확인이 NetworkPolicy에 막힘)을 찾고 → 수정·랩 회귀까지 마침. Kind는 정책을 적용하지 않아 못 잡는다.
- **말할 것.**

  > VM 랩에서는 연결을 유지하지 못하는 결함도 찾았습니다. 같은 Pod 안에서는 괜찮았지만 다른 노드에서 연결하면 끊겼고, 네트워크 정책을 끄면 문제가 사라졌습니다.
  > 원인은 서버가 상대의 생존을 확인하는 TCP 7번 패킷을 정책이 막는 것이었습니다. 필요한 경로만 허용한 뒤, 노드를 건넌 세션 40개와 Broker를 거친 연결 30개가 세 차례 대기 후에도 유지됐습니다. 이번 Kind 환경은 이 정책을 적용하지 않았기 때문에 놓쳤습니다. 자동 시험과 실제 환경 시험을 함께 해야 하는 이유입니다.

- **넘어가기.** "막지 못한 것도 보여 드리겠습니다" → 13장.
- **질문 나오면.** 예상 질문 8번.

### 13. 차단 전에 성공한 쓰기는 새 master에 없을 수 있습니다  (30초)

- **요지.** 13건·최대 73건은 성공 응답을 받았지만 새 master에 없는 데이터다. 전체 서버에서의 최종 손실과 구분한다. 28초는 정상 종료 때 불필요한 격리(Kind).
- **말할 것.**

  > 막지 못한 사례도 있습니다. 복제를 멈춘 뒤 VM 전원을 차단하자, 성공 응답을 받은 데이터 13건이 새 master에 없었습니다. 옛 master 디스크에는 남아 있었습니다. 네트워크 분할 시험에서는 새 master에 최대 73건이 없었습니다. 모두 쓰기 경로를 닫기 전에 승인된 데이터입니다.
  > 반대로 정상 종료 때 불필요하게 쓰기가 28초 막힌 Kind 기록도 있습니다. 데이터 보존과 중단 시간 모두 개선할 여지가 있으며, 이 결과를 시험 조건과 함께 공개합니다.

- **넘어가기.** 전환 장 → v0.1.
- **질문 나오면.** 예상 질문 5, 6, 13번.
